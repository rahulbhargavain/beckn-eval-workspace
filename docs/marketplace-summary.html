Decentralised marketplaces: where the work stands

Status report, 28 October 2026. Draft for review. Work in progress, not a product.

We are testing whether an open, server-to-server transaction standard can run marketplaces without a central platform in the middle. The standard under test is Beckn Protocol 2.0.0, which is itself still a draft. We judge it by running the same tests against any system that implements it, not by what anyone claims about it. So far the only system tested is our own reference network. One practical application, a Himalayan smallholder produce hub, shows where the standard helps and where it does not.

What exists

Test harness

A certification-style test runner

Sends signed requests to a system under test, deliberately sends faulty ones (forged signatures, repeated messages), checks the signatures on its replies and, in one optional test that runs on the same machine, on its callbacks (the replies that arrive later as separate messages), and issues signed reports. The registry's admission check works out the verdict again for itself, so an edited or partial report is refused.

Reference network

A small working network

A buyer app, a seller node and a registry running together on one machine, covering discovery, quoting, ordering, confirmation, status, update and cancellation. It exists to prove that the tests themselves work.

Domain packs

Catalog formats for agriculture, energy and tourism

Thin schemas, with the rules each network may impose kept in a separate policy file. New domains are added as data, with no change to the core code.

Onboarding

Signed registry files

A tool that builds and checks the signed files a participant publishes so others can find and verify it. Not yet cross-checked against a second implementation.

Stock

A lot ledger for a produce hub

Records graded lots with their source households, publishes a catalog of what is actually on hand, and stops the seller node from selling the same kilograms twice.

What testing has shown about the standard

  • Lost results are an open question. If a request is acknowledged but the result never arrives, the specification marks the question "to be announced" and gives no retry or timeout rule. Our workaround is to ask for the status again, which means resending the full order details.
  • Callback addresses are a security risk. The specification requires public HTTPS addresses that match the registry, but it never tells the receiving system to check for private addresses, redirects or address-lookup tricks before it calls them, so each implementer must add that guard.
  • Quantities are open. The standard does not constrain them, so fractional quantities such as 12.345 kg need a rule from the network. Ours is decimal arithmetic with at most three places.
  • Ten tests are expected to fail until the specification is corrected. Each records a gap, contradiction or error in the specification's own files. We track them as findings about the standard, not as defects in our code, and have not yet reported them to the specification's authors.

Application: a Kumaon smallholder produce hub

The smallholder value-chain design published on cottonspace.com proposes collection, grading, assaying, vacuum packing and a sealed-bid spot-auction layer at a hub in Bhimtal. That note describes a proposal and small pilots. It reports no measured farmer prices or incomes, and its aggregation facility exists as a submitted project report. Our work maps onto it as follows.

What this does not claim

  • No live network has been joined and no real transaction has taken place. This is a test environment.
  • Our catalog formats are our own and have not been checked against the upstream community schemas.
  • The ONDC material we reviewed uses an earlier protocol version that is not wire-compatible with 2.0 (messages from one cannot be read by the other).
  • Only the agriculture catalog format has been exercised with real use in mind; the energy and tourism formats are placeholders.
  • This is independent work. It is not endorsed by ONDC, NeML, NeSL, the Beckn or NFH community, or any public body.
  • Tests ran on one operating system plus one earlier trial on a rented Linux server; the latest changes have not been re-run on Linux.
  • The lot ledger is in memory only and is a design aid, not a system of record.
  • We have no evidence that this approach improves what smallholders are paid. Recording price by grade by lot is how that evidence could start to exist.

Next steps

  • Make the ledger durable (it currently forgets everything on restart) and let a quote reserve stock briefly before the order is confirmed.
  • Suggest an unambiguous encoding for the bid commitment in the design's proposed auction, since joining fields end to end before hashing can be read more than one way.
  • Align our catalog formats with the published Beckn community schemas.
  • Join a test network once a counterparty is willing to trade, and compare results with the same tests.
